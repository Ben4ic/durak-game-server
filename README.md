# durak-game-server v2

## Что было не так (аудит 4 архивов)

- **durak-game-server (main)** — реально задеплоенный на Render бэкенд.
  `server.js` — только заглушка: комнаты в `const rooms = {}`, эндпоинт
  `/api/online/action` вообще ничего не делал (`res.json({ok:true})`).
  Игры как таковой на сервере не было.
- **Durak-Online-MVP-v1** — заброшенная попытка новой структуры
  (`rooms/`, `game/`, `storage/redis.js`). Но `game/engine.js` — пустой
  класс-заглушка (`start(){ this.state="playing" }`), `redis.js` не
  использовался нигде. По сути тоже пустой каркас.
- **durak-online-client (main)** и **durak-online-PVP-v2-render-fixed**
  — это один и тот же Next.js фронтенд (второй чуть новее, 3 файла
  отличаются). Оба проксируют `/api/online/*` на бэкенд через
  `lib/backendProxy.ts` → `GAME_SERVER_URL` (Render).

**Главная находка:** на фронтенде, в `lib/multiplayerDurak.ts`, уже
лежит полностью рабочий движок дурака (колода, козырь, атака/защита/
"бито"/"взять", подсчёт победителя, ревизии состояния) — просто он не
был подключён ни к какому реальному бэкенду. `app/online/game/[code]/
page.tsx` уже написан под его формат ответа (`publicOnlineState`) и
поллит `/api/online/room` каждые 500мс — то есть контракт клиент↔сервер
уже был спроектирован правильно, не хватало только настоящей
реализации на сервере.

## Что сделано в v2

Backend полностью переписан на реальную логику, эндпоинты **не
поменялись** — фронтенд трогать не нужно:

```
src/
 ├── server.js            — express-роуты, 1:1 повторяют старый контракт
 ├── rooms/roomManager.js — комнаты, токены игроков, TTL-очистка
 ├── game/engine.js       — движок дурака, портирован из lib/multiplayerDurak.ts
 └── websocket/socket.js  — необязательный WS push (Этап 3, задел на будущее)
```

- `/api/online/create|join|quick|leave|rejoin|public|room|action` — те
  же пути и тот же JSON-контракт, что ожидает текущий фронтенд.
- Комната теперь честно хранит **состояние игры** (колода, козырь, руки
  игроков, стол, кто атакует/защищается), а не просто список игроков.
- `/api/online/action` реально применяет ход через движок и отдаёт
  игроку **только его руку** (защита от подглядывания через сеть).
- WebSocket сервер поднят и рассылает `STATE_UPDATE`, но клиент пока
  им не пользуется (работает поллингом) — это задел под Этап 3, можно
  включить позже без переделки комнат/движка.

Проверено локально (без npm, чистой логикой): создание комнаты, join
второго игрока → игра стартует, атакующий делает ход → состояние и
revision обновляются корректно.

## Прогон на баги (edge-cases), после первого деплоя

Нашёл и исправил 2 реальных бага при прогоне через нагрузочные/граничные
сценарии (обрыв связи, повторный клик, полная комната и т.д.):

1. **Дублирующийся список игроков.** У комнаты было два отдельных массива
   игроков — `room.players` и `room.game.players` — которые вручную
   синхронизировались в паре мест. Само по себе пока не стреляло (ровно 2
   игрока, один join), но было миной на будущее (3+ игроков,
   переподключение). Теперь единственный источник правды —
   `room.game.players`, дублирования нет.
2. **"Мусорное" действие тихо проходило.** Если `action` в
   `/api/online/action` был не `play`/`done`/`take` (например, из-за бага в
   клиенте), сервер не менял состояние, но всё равно увеличивал `revision`
   и отвечал успехом — это маскировало бы реальные баги клиента. Теперь
   такой запрос сразу отклоняется с `UNKNOWN_ACTION`.

Проверено 13 сценариев (все прошли): двойной клик по одной и той же карте,
мусорный action, ход не в свою очередь, обрыв соединения и возврат в игру
по тому же токену, попытка зайти в заполненную комнату, выход соперника
посреди игры (оставшийся автоматически побеждает, его токен остаётся
рабочим, токен ушедшего отзывается), выход из комнаты до старта игры
(комната корректно удаляется), быстрый поиск игры "quick join" двумя
игроками подряд.

Всё это будет системно намного крепче с Redis + правильным reconnect по
таймеру — это следующий логичный шаг, если баги вылезут в реальном
использовании.

## Redis (комнаты переживают рестарт сервера)

Добавлено хранилище `src/storage/roomStore.js` с двумя реализациями за
одним интерфейсом:

- **MemoryStore** — то же поведение, что было раньше (`Map` в памяти
  процесса). Используется автоматически, если `REDIS_URL` не задан —
  ничего не ломается для тех, кто ещё не подключил Redis.
- **RedisStore** — то же самое, но в Redis. Комнаты и партии переживают
  рестарт/редеплой/краш процесса вместо того, чтобы обнуляться вместе с
  памятью.

`roomManager.js` целиком переписан на `async/await` и обращается только к
этому интерфейсу — ни `Map`, ни Redis-клиент напрямую нигде не
используются за пределами `roomStore.js`.

Отдельно обработана гонка при одновременном join: `joinRoom` идёт через
`store.withRoom()`, который в Redis-версии использует `WATCH`/`MULTI`/
`EXEC` с ретраями — это единственное место, где реальная гонка (два
игрока одновременно становятся "вторым игроком" одной комнаты) могла бы
сломать инвариант "ровно 2 игрока". Проверено на mock-клиенте Redis
(эмуляция конфликта записи + повторной попытки) — данные обеих сторон не
теряются.

Как включить: на Render добавь Redis (например, встроенный Render Key
Value, или внешний вроде Upstash) и пропиши его URL в переменную
окружения `REDIS_URL`. Без этой переменной сервер работает как раньше.

## Пользователи + авторизация через Telegram

Добавлен модуль `src/auth/telegram.js` — проверка подписи Telegram Mini
App `initData` по официально документированному алгоритму Telegram
(HMAC-SHA256 секретом, выведенным из токена бота). Он доказывает, что
запрос действительно пришёл от конкретного Telegram-пользователя, а не
подделан на клиенте.

`GET /api/auth/me` теперь: если клиент прислал заголовок
`Authorization: tma <initData>` — сервер проверяет подпись и возвращает
настоящий Telegram-профиль (id, username, имя, фото). Если заголовка нет
— тот же анонимный "guest", что и раньше (ничего не ломается для текущего
фронтенда, который пока эту авторизацию не отправляет). Если заголовок
есть, но подпись не сходится — `401`, а не тихий откат на гостя (иначе
подделанный заголовок был бы неотличим от отсутствия авторизации).

Настройка: `TELEGRAM_BOT_TOKEN` в `.env` (получить у @BotFather). Без
него `/api/auth/me` продолжает работать как раньше — просто без реальной
Telegram-идентификации.

Проверено 13 сценариями на вручную подписанном тестовом `initData` (раз
нет доступа к настоящему Telegram из песочницы): корректная подпись
принимается, подмена данных после подписи отклоняется, чужой токен бота
отклоняется, протухший `auth_date` (замена старых данных) отклоняется,
подделанный заголовок даёт 401 вместо тихого отката на гостя.

**Сознательно не сделано в этом заходе:** Telegram ID пока не
привязывается к игроку внутри комнаты/движка. Если это сделать сейчас,
объект игрока (который целиком уходит и своей стороне, и сопернику через
`publicOnlineState`) утёк бы Telegram ID оппоненту — приватность. Разумно
делать эту привязку вместе с БД пользователей (Postgres, следующий пункт
ТЗ), где это будет храниться на сервере, а не путешествовать в открытую
внутри игрового состояния.

**Из ТЗ на экономику (`TZ_Durak_Online_Game_Economy`):** пункты 1
(пользователи/авторизация) сделаны в объёме выше. Баланс, транзакции,
платёжный модуль (Crypto Pay/Stars с вебхуками пополнения) и списание
ставки/выплата победителю — сознательно не делаются: подтверждено, что
победитель забирает взнос обоих игроков, то есть это ставки на реальные
деньги (независимо от того, что валюта "внутриигровая" — она покупается
за реальные деньги и разыгрывается), для этого нужна лицензия на
азартные игры, обсуждается отдельно с юристом, не мной.

## Что осталось по плану из ТЗ (не сделано в этом заходе)

- **PostgreSQL** (users/balance/transactions) — не трогали, в текущем
  контракте нет ставок/баланса.
- **Правила "подкидной для нескольких игроков"** (подкидывание чужими
  картами, "перевод") — движок сейчас 1v1 (ровно как во всех 4
  архивах), для 3+ игроков потребуется отдельная доработка.
- **Telegram Stars/TON для покупки цифровых товаров** — не в этом
  контракте (см. отдельное обсуждение про азартные игры/ставки —
  этого сервер сознательно не делает).

## Запуск

```bash
npm install
cp .env.example .env
npm start
```

Задеплоить можно точно так же, как раньше (Render), просто заменив
содержимое репозитория `durak-game-server` на эту папку.
